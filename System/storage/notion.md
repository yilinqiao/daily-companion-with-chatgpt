# Notion storage (recommended)

One private Daily Companion Suite is the live source of truth. GitHub is needed only to read the public release at setup/update, never as a second personal store. Do not fall back to GitHub or another workspace on a Notion failure. All logical System paths resolve to the private System pages via the verified page-ID mapping in the suite's System index; scheduled prompts pin that index and their entrypoint. Never expose private IDs outside the user's private installation.

## Setup and permission proof

Before writing, verify the Notion connection with a harmless scoped read; guide the user to connect Notion and grant the selected private parent/suite full access needed to search/read/create/update pages, database/data sources, properties and views, query rows and read back writes. Do not request workspace-wide access when a scoped grant suffices. If a required connector operation is unavailable, explain which capability is missing and help connect/retry; do not assume UI support or claim setup complete. Explicit summary approval authorizes the following actual creation and verification, not arbitrary workspace edits.

Create or reuse a private page "Daily Companion Suite" and exactly these three data sources under it. Confirm identities, inspect existing schemas and views, reuse unambiguous matches, propose conflicts before changing existing user schema. Never publish/share, delete, or create duplicates on retry. Create real data sources and views through supported operations; if view operations are not exposed, guide the user through creating the missing views and verify by reading them back where supported. Do not call a text description a created view.

## Daily storage and Calendar identity

Verify profile's notion_daily_autosave_authorized is explicitly true before every scheduled auto-save; missing/false means read/output only. Revocation is an interactive profile update, verified by read-back. Daily unique key = local As of date + Category (not title alone). Use actual scheduled occurrence's local date. Query by both fields, paginate, stop on multiple matches or unreadable state. Initial auto-save creates a single page with Status Auto-Saved and correct title/date/category/body; do not overwrite an existing Edited/Imported page or existing Auto-Saved snapshot on a replay. Verify exact page ID, properties, content and source mapping after write; only claim success if read-back succeeds. A failed save does not invalidate the human check-in; report material failure and offer authorized interactive recovery. No automatic cross-store backup.

Morning: render the normal human-readable Briefing in the chat (no Markdown file preview requirement). Before auto-save preserve actual Calendar IDs/links from approved included calendars. If frozen identity is missing, use artifacts.md narrow identity-only recovery (original title and exact original start/end, unique across included calendars; never guess). Append a final Notion-only section called `Calendar ID` containing the exact calendar_id + event_id, original title/start/end, and provider link when returned, one record per confidently mapped event. When none is available, record the actual reason/no events, never invent IDs or links. Keep section out of all chat output and approval previews. It is the original Morning snapshot, not the current Calendar state. Evening reads this section and performs exact event lookup first. All user edits to the Briefing preserve this section byte-for-byte/logically unchanged; fresh-read it before any revision, change only the approved visible body, preserve unrelated page metadata, read back and verify both. Do not delete or silently regenerate it. If it is missing on an existing older page, report incomplete linkage; only repair if original identity is uniquely recoverable and user explicitly approves.

Evening: auto-save an initial Diary-first provisional Daily Memory using only supported evidence, mark Auto-Saved, then present ordinary conversational check-in ending in three questions; no initial full Markdown preview or approval panel. Do not store guesses as completed actions. After user answers, fresh-read the same page; display full revised Markdown and independent Ledger proposal, use explicit approval panel/text fallback. On approval update same page, not a new row. Preserve user edits; if changed since preview, reconcile and get fresh approval. Read back content, then set Status Edited and verify status. If save/status verification fails, report partial result and never claim Edited. An explicit user-approved revision to Morning follows the same fresh-read/verify pattern. Provisional records are useful historical context, not proof of completion or user confirmation; Sunday labels them accordingly.

For Ledger, use current source properties and fresh rows, update only authorized fields, preserve unrelated data; verify row ID, exact stable Task ID, Status and changed values. Never create duplicate rows or invent dates/property options; never close based on provisional notes. No scheduled Ledger mutations.

## Extra (read-only)

Use the Surprise engine Creation Rules and Manual Mode, but do not use GitHub's v6 claim/date-write protocol. During approved setup choose a private anchor Monday in the first complete week after setup and an arbitrary 104-character sequence of digits 1–7 (one per Monday–Sunday week). Store only private anchor, pattern and enabled state in the private engine page, not in public templates or chat. Validate length/digits/week anchor during setup. For Auto, resolve actual scheduled local occurrence date; before anchor stop silently; calculate elapsed whole weeks since anchor, index modulo 104 (zero-based), and compare digit with local weekday (Monday=1). Only that date qualifies. Check enabled is true and anchor/pattern valid before evaluating; if disabled stop silently, invalid report failure. No catch-up on missed dates, no state write or manual replay on uncertain occurrence, no exact-once claim (platform retries may duplicate). One task, no overlapping schedules. Pause/resume changes only enabled interactively after fresh read; manual surprise does not consume a date. Never show future dates/pattern. Style feedback can be saved interactively only on explicit request. Update Watch stays read-only.
